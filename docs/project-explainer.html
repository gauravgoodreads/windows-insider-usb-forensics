Can the small traces Windows leaves behind tell an ordinary USB backup apart from someone copying sensitive company files to a USB drive?

The question

The idea in one minute

Think of a detective at a crime scene. One footprint does not prove who did it. But a footprint, a fingerprint, a CCTV clip and a receipt that all point to the same person at the same time make a strong case.

Windows works the same way. Every time someone plugs in a USB drive, opens a file or copies something, Windows quietly writes small records in different places. We call each record an artifact. One artifact alone proves very little. This project collects many artifacts, puts them on one timeline, and checks whether they agree with each other.

The main lesson of the project

Plugging in a USB drive is normal. It happens in both the innocent and the suspicious experiment. So "a USB was used" is weak evidence. The case becomes strong only when several independent clues agree inside the same USB time window, especially a copy of the sensitive file appearing on the USB itself and the user's login session at that time.

What the project does

  • Compares one normal and one suspicious scenario on the same PC, user and USB drive
  • Collects real evidence from any Windows PC with a read-only script, with no virtual machine needed
  • Keeps the evidence safe with hashes and a custody log
  • Reads Windows artifacts, joins them, and judges four questions (H1–H4)
  • Shows everything in a dashboard and in PDF, HTML and CSV reports

What it does not do

  • It does not spy on any real person
  • It uses no real company data. Every "sensitive" file is fictional
  • It never says someone is guilty or explains their motive
  • It does not claim to be ready for use in a real court
The method

Two experiments, one clean starting point

A good experiment needs a control: a normal case to compare against. Both experiments use the same computer, the same user, the same USB drive and the same fictional files. So the only real difference between them is what the user did.

Experiment A · the control

Normal USB backup

The user logs in, plugs in BACKUP_DRIVE, copies an ordinary Readme.txt, and unplugs the drive.

Experiment B · the simulated incident

Copying fictional sensitive files

The user opens fictional salary and customer files, copies them to the USB, makes a ZIP archive, and deletes a temporary copy of a project file.

USB activity appears in both experiments. That is why the project never treats "USB was used" as proof of copying.

The method

How the whole system works

The project is built in four layers, and they are kept apart on purpose. The layer that creates the activity is never used as proof. Proof comes only from the evidence that was preserved and then examined.

Figure 1. The four layers. Blue boxes are the most important steps to point at when explaining.

Normalization, in simple words

Different Windows tools write their records in different shapes. One calls a field "DeviceName", another calls it "FriendlyName". Normalization rewrites every record into one common form, with the time, user, file, device and activity. If a value is missing, it stays missing. Nothing is guessed. The original raw record is always kept next to it.

Correlation, in simple words

Correlation means joining records that belong together: same user, same USB, same file, close in time (within a 20-minute window by default). Each joined group is saved with the IDs of the records it used and a plain-English reason. So anyone can check why the engine made the link.

The result

The four questions and their answers

The project does not give a single "guilty / not guilty" answer. It asks four separate, careful questions, called hypotheses H1 to H4. Each answer comes with a confidence label and a limitation.

QuestionResultConfidenceIn simple wordsLimitation to mention
H1 Was a USB drive used?SupportedHighSeveral records show the USB being connected and removed.Using a USB is normal. It happens in Experiment A too.
H2 Were the sensitive files accessed?SupportedMediumShortcut and recent-document records show the fictional salary and customer files being opened.Opening a file is not the same as copying it.
H3 Is there corroborated copying during the USB window?SupportedHighUSB, file access, the file on the USB, the ZIP and the login all agree within the same window.Correlation shows timing and links, not intention.
H4 Is there hiding-like activity?Partially supportedMediumA ZIP was made and a file was deleted.People zip and delete files for normal reasons too. Intent cannot be proved.

Low, Medium and High are labels defined by this project. They are not probabilities and not an industry standard.

The one-line conclusion to give

"In this controlled dataset, several independent Windows artifacts together separate the simulated sensitive transfer from normal USB use much better than any single artifact, but real uncertainty and limits remain."

Evidence safety

Keeping the evidence trustworthy

Hash = digital fingerprint

A SHA-256 hash is a long code calculated from every byte of a file. Change even one byte and the code changes completely. We record the hash when the evidence is collected and check it again later. If they match, the evidence was not changed. A hash detects change. It is not encryption and does not hide anything.

Chain of custody

A log of who handled the evidence, when, and what they did, for example "Acquired and sealed". The project also keeps an audit log of what the investigator tool did. Analysis always uses verified copies, never the original image.

python acquisition\hash_evidence.py   <image> --evidence-id EVD-001
python acquisition\manifest.py        custody.json --evidence-id EVD-001 --handler "Student Investigator" --action "Acquired and sealed"
python acquisition\verify_evidence.py <image> --manifest EVD-001.json

For the viva

Questions sir may ask, with simple answers

Where does your evidence come from?

Two places. First, a controlled dataset of two scenarios with fictional data, so the right answer is known in advance. Second, a real run of both experiments on my own laptop with an external USB disk, collected by a read-only script. The real evidence gave the same verdict as the designed dataset.

Why two experiments?

Experiment A is the control. Without it, I couldn't show which clues are normal. Because USB use appears in both, I can show that USB alone is not proof.

Does the USBSTOR Registry key prove the file was copied?

No. It only shows that a device with that identity was connected at some point. It needs support from file, destination, time and user evidence.

Does a timestamp prove copying?

No. Windows timestamps mean different things (created, modified, accessed) and can change when files are copied, opened, or when the clock is wrong. Timestamps help with order, not proof.

Why do you use many artifacts?

Each one can be missing or unclear. When several independent ones agree, the conclusion is much more reliable. This is called corroboration.

What is normalization?

Converting records with different field names into one standard format, without guessing missing values. The original record is kept as well.

What is correlation?

Linking records that share a user, device, file or time window, using fixed rules. A correlation shows a relationship, not cause or intent.

Isn't collecting from a running PC risky for evidence?

Yes, any live collection touches the system a little. That is why the collector only reads, hashes its own output, and the project states this as a limitation. For formal casework you take a powered-off disk image instead and analyse a verified copy; the same pipeline reads exports from either.

What is a hash and why do you need it?

A digital fingerprint of the file. If the hash matches the recorded value later, the evidence has not changed since collection.

Is the score of 13 a probability of guilt?

No. It is a simple, visible checklist made for this project to help rank findings. It is clearly labelled as not a forensic standard.

Can this be used in a real court?

Not directly. Real cases need validated tools, legal authority and real-world variety. This project shows the method on controlled, fictional data.

What are the main limitations?

Fictional data, one controlled Windows setup, results depend on which artifacts were exported, timestamps can be unreliable, artifacts can be missing, there is no validated statistical model, and it never infers motive or guilt.

What makes your project reproducible?

Versioned code and settings, a fixed scenario dataset, a scripted read-only collector, evidence hashes, raw records kept, source IDs on every conclusion, fixed rules, 14 automated tests and generated reports.

Why didn't you use a virtual machine?

The analysis does not need one. It reads exported artifacts from any source. A VM would only be a way to create test evidence, and the scenario dataset plus the read-only collector already give a known-answer test and a real-world test without the extra setup.

Is the demo data real?

The two scenarios are a clearly labelled controlled dataset, so the correct answer is known in advance. The real run is genuine Windows evidence from my laptop: real USB connections, real shortcuts, real files on the USB disk and a real Recycle Bin record. Only the company files themselves are fictional.

Reference

Glossary

Artifact
A trace or record Windows leaves behind, such as a Registry entry, shortcut or log line.
Insider exfiltration
Someone inside an organization taking data out without permission.
USBSTOR
The Registry area where Windows remembers USB storage devices that were connected.
LNK file
A Windows shortcut file. It is created automatically when a file is opened and shows that the file was used.
Jump List / Recent docs
Lists of recently opened files that Windows keeps for each program.
Prefetch
Files Windows uses to start programs faster. They show that a program was run, and when.
Shellbags
Registry records of which folders a user browsed in File Explorer.
Recycle Bin
Where deleted files go. It keeps a record of the file name and deletion time.
Event log
Windows' diary of system events, such as logons and device connections.
Live triage
Quickly collecting evidence from a running computer, read-only, instead of imaging the whole disk.
Disk image
An exact byte-for-byte copy of a disk, taken for examination.
SHA-256 hash
A digital fingerprint used to show a file has not changed.
Chain of custody
A record of who handled the evidence and what they did with it.
Normalization
Converting different record formats into one standard format.
Correlation
Linking related records by time, user, device or file.
Hypothesis
A careful question tested against the evidence (H1–H4).
Provenance
Where a piece of information came from, so it can be traced back.
Control experiment
The normal case (Experiment A) used for comparison.
